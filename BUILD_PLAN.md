## TL;DR

- **Not waterfall. Vertical slices on a dev → test → dev → test loop.** A slice is migration + RLS policy + pgTAP test + server code + UI + Playwright flow, taken to green before the next one starts. Nobody builds "all the backend" then "all the frontend".
- **Day 1 is the only hard ordering constraint in the plan.** The FORCE-RLS meta-test, the `audit_row()` substrate and term scoping are the ground every later slice is written against. Written afterwards, the meta-test is written against a schema that already violates it and gets weakened to pass. Everything after Day 1 loops freely.
- **Done means the tests are green, not that a screen renders.** And a security test that has never been *observed red* is a test you do not know works — every guard in this plan carries a named red-verification step. Skipping it is the one shortcut that is never allowed.
- **The biggest risk is Google Drive on Day 3** (OQ-1 is unanswered — the org may not even have a Shared Drive). It is hard-timeboxed to 12:00 with a pre-agreed fallback that is an environment-variable flip, because the Supabase Storage implementation *and its bucket migration* ship the same morning.
- **Day 7 is buffer, not work.** If you are writing features on Monday the plan has already failed — cut scope on Saturday instead, from the pre-agreed drop list in each slice's risk table. Cut UI. Never cut a pgTAP suite.

## The loop

Every slice runs this cycle. It is the unit of work, not the day.

| # | Step | What | Delegable to a subagent? |
|---|---|---|---|
| 1 | **Migration** | Table + `ENABLE` **and** `FORCE ROW LEVEL SECURITY` + column GRANTs, one logical change per file, mandatory header comment (CONVENTIONS §9 D2) | Yes — one agent, one file. Never two agents in `supabase/migrations/` at once. |
| 2 | **Test** | pgTAP: exact row counts **and** exact visible column sets, per role fixture. Never `> 0`. | Yes |
| 3 | **RUN IT** | `pnpm test:rls`. Red is information; green is permission to continue. | **No. You read the output yourself.** |
| 4 | **Verify the red** | Break the thing the test guards — drop a policy predicate, revoke a `FORCE`, add a `DELETE` policy — confirm the test fails, revert. | **No.** |
| 5 | **Server code** | Server Action opening with `withRole([...])`, or a `SECURITY DEFINER` RPC with `SET search_path = ''` and a deny test per role | Yes |
| 6 | **UI** | The screen. Server Components read PII; client leaves never do. | Yes — 2–3 agents in parallel on distinct component files |
| 7 | **RUN IT** | `pnpm test:e2e` for the path a human takes | **No.** |
| 8 | **Fix → 3** | Loop until green, then and only then take the next slice | — |

**Never batch step 8.** A slice carried forward red is a slice whose failure gets attributed to the next slice's code — and on a seven-day clock you will not go back and find out.

With Claude Fable, steps 1–2 and 5–6 are cheap enough to fan out. **Steps 3, 4 and 7 are never delegated.** A subagent reporting "tests pass" is a claim; the terminal is evidence.

## S2 — Wed 2 Sept · Authorization spine

*The security foundation, the heaviest test day, and the one worth protecting from scope pressure. **Policy authoring does not parallelize** — S2-T15 through S2-T19 all append to `0014_rls.sql` and are strictly chained.*

**At the end of this slice that did not exist before:** the database is the authorization boundary and can *prove* it — nine role fixtures asserting exact row counts and exact visible column sets, CI-blocking. The Constitution is data: 18 regions, 23 CBL positions with the four-administrator CHECK, seven Art. III §4 departments, one active term. ## S3 — Thu 3 Sept · Public application intake

*Highest attack surface: unauthenticated, public, accepts uploads. Also the highest-risk day — the fallback is pre-agreed and hard-timeboxed.*

**At the end of this slice that did not exist before:** an anonymous person on a phone can open `/apply`, fill personal + academic + membership sections, consent to the privacy notice, upload a 6MB photo of their Certificate of Registration **straight to storage without those bytes crossing a Vercel function**, and see the success-and-pending screen — while the same link is inert *in the database* when no window is open. ## S4 — Fri 4 Sept · Review → approve → member ID

*Day 3 ends with applications that can only be written, never read or decided. This slice is what makes them decidable.*

**At the end of this slice that did not exist before:** an application submitted on Day 3 can be found, filtered, opened, read in full, its Certificate of Registration **viewed in-browser through a route that authorizes by RLS and audits every single view**, then approved or rejected with a reason. Approval mints a `joinYear-sequence` member ID **in one transaction that also creates the `people` and `memberships` rows**, allocated by a single-statement counter-table upsert that survives 50 simultaneous approvals with zero duplicates and zero gaps, and returns the *existing* ID for a person who already has one so renewal can never renumber.

**Migration ledger for today:** `0022_member_id_allocation` · `0023_approve_application` · `0024_reject_application` · `0025_document_view_audit` · `0026_application_detail_rpc` · `0027_applications_review_grants`

## Parallelism

### Safe to run concurrently

| Lane | Why it is safe |
|---|---|
| Two or three UI agents on **distinct component files** within one slice | No shared file, no shared DB object. Their integration point is the Server Component page, which one agent owns. |
| pgTAP test authoring on **distinct numbered files** | `supabase/tests/0NN_*.sql` are independent; the shared `helpers/` are written once (S2-T14) and then read-only. |
| Docs, ADRs, runbooks, the privacy notice | No code dependency. S7-T21 and S7-T25 can run all Sunday alongside the deploy work. |
| `lib/<feature>/{schema,queries,types}.ts` in different feature folders | Feature folders, not layer folders, exist exactly so this is true. |
| The three document-store implementations (S3-T9/T10/T11) | One interface, three files, one shared contract test. |

### Must merge alone — one agent, one branch, no concurrent second writer

| Lane | Why |
|---|---|
| **`supabase/migrations/**`** | Two agents authoring migrations at once produce filename collisions and apply-order surprises. **One migration author at a time, all week.** |
| **`0014_rls.sql`** specifically | S2-T15→T19 are chained. **Concurrent policy edits are how a boundary gets silently widened while every test still passes** — the failure mode with no error message. |
| **`supabase/tests/helpers/fixtures.sql`** | Eleven test tasks read it. A concurrent edit changes expected counts under files that are already green. |
| **`database.types.ts`** | Generated, committed with its migration, verified by the `types-drift` job. Never hand-edited, never merged. |
| **`eslint.config.mjs`'s `no-restricted-imports` rule** | CLAUDE.md: *"if you find yourself editing that rule, stop and ask."* |
| **`middleware.ts`** | One owner (S2), extended by S2-T37 and read by S3-T17. |

### Never delegated — you read the output yourself

- **Reading test output.** A subagent reporting "tests pass" is a claim; the terminal is evidence.
- **Every red-verification step** — S1-T17, S1-T16, S2-T20, S2-T42, S3-T14, S3-T23, S4-T8/T23, S5-T2, S5-T8, S6-T3, S6-T15, S6-T20, S7-T9, S7-T10, S7-T26. **A security test that has never failed is a test you do not know works**, and a subagent will cheerfully report the green half.

- **The restore drill** (S7-T16) — and specifically by a **human who did not write the script**, following only the runbook. That is the test.
- **Any decision that would widen a policy, a GRANT, a view, or the service-role blast radius.** If the answer looks like widening something, the answer is wrong; escalate instead.

### RA 10173 — mechanisms vs paperwork

**This distinction is the single most important honesty in the submission, and it is not a hedge.**

- **The mechanisms ship and are tested.** Sensitive columns classified as data in a registry that CI checks against the live catalog; column GRANTs and a directory view drawing the boundary twice; RLS with FORCE on every table and no DELETE policy anywhere; an append-only audit log whose sensitive values are **masked before they are written**, so the log is not itself a PII store; an audit row for **every** proof-document view (item 16, RA 10173); the 5-year purge on both sides of the storage boundary; a Sentry scrub proven against a real client; encrypted off-provider backups **with one restore actually performed**; a published privacy notice; consent captured at collection against an **immutable** notice version, enforced by a database CHECK; a pre-drafted 72-hour NPC breach notification; and the CBL Art. VIII §7 confidentiality-acknowledgement gate on every sensitive read.
- **The paperwork has not started, and cannot be finished in seven days by engineers.** No DPO is designated and the org is not NPC-registered (OQ-2 — an external filing that takes weeks and requires the *organization* to designate an officer). No DPA is executed with any of the seven processors, because each needs a signature from an authorised org signatory, which needs the DPO decision first. The retention clock's start date is unsigned (OQ-8). The quarterly restore-drill **cadence** is by definition not demonstrable in a week — one drill is. And every console created this week sits on a personal identity (OQ-9, OQ-10).
- **Therefore:** no document in this repo claims RA 10173 compliance, `grep` enforces that (S7-T24), and the stated position is that **the system must not collect real applicant data until the DPO, the DPAs and the org-owned identities are in place.** Saying this plainly is cheaper than being asked about it.
