# ADR 0010 — Outbound mail goes through a transport interface; the first transport is Gmail SMTP

**Date:** 2026-09-06
**Author:** Ethan Baltazar (project head), with Danielle Quiambao (CCDO) on the account side
**Status:** Accepted — and explicitly interim. Resend remains the locked-stack vendor
(`ARCHITECTURE.md` §1); this ADR records why it cannot be used yet and what stands in
until it can.
**Deviates from:** `ARCHITECTURE.md` §1 "Integrations" — Resend for *all* outbound email.
**Implemented by:** `lib/mail/` (`types.ts`, `fake-transport.ts`, `gmail-smtp-transport.ts`,
`index.ts`), the `MAIL_TRANSPORT` / `GMAIL_*` / `MAIL_*` variables, `nodemailer` 9.1.1
(exact).

---

## Context

The locked stack sends every email through Resend. Resend delivers from a **verified
domain**, and START-DOST does not own one yet (PRD OQ-10). Resend's onboarding sender can
only mail the account owner's own address, which is useless for a demo that sends
application, renewal and committee forms to scholars. Meanwhile the CCDO's SRS
(2026-09-05) needs "CRRD can use the platform to directly send emails with an HTML
format attached" and to filter recipients — the outreach half of the system, which has
been unbuilt because its transport was blocked on a domain.

The org does have a working sending identity: the START community account, a consumer
`@gmail.com` mailbox. The team's first thought was the Gmail API. It does not fit:

- `gmail.send` is a **restricted** OAuth scope. Google blocks unverified apps on it, and a
  consent screen left in "Testing" issues refresh tokens that expire after seven days —
  the same silent-Monday-death `ARCHITECTURE.md` §4.1 records for the Drive fallback.
- The account holder would have to run an OAuth consent flow against a Google Cloud
  project the org does not control long-term.

SMTP with a Google **App Password** has none of that: 2-Step Verification on the account,
one 16-character secret generated by the account holder, TLS on port 465, no consent
screen, no token lifetime.

## Decision

1. **A transport interface, not a vendor call.** `lib/mail/types.ts` defines
   `MailTransport { send, ping }` with no provider vocabulary. Campaign code, templates
   and the send loop only ever import `lib/mail`. This mirrors `lib/documents/` and
   exists for the same reason: the vendor is an env-var flip.
2. **`MAIL_TRANSPORT` selects the implementation.** `fake` (tests, Playwright, previews —
   records, never delivers) and `gmail_smtp`. Adding `resend` later is one file and one
   enum member.
3. **`gmail_smtp` uses `nodemailer` over `smtp.gmail.com:465`** with the App Password from
   `GMAIL_SMTP_APP_PASSWORD`, sending as `"MAIL_FROM_NAME" <GMAIL_SMTP_USER>` with an
   optional `MAIL_REPLY_TO`. One pooled connection per process; nodemailer's logger and
   debug output stay off so no recipient or body ever reaches the function logs.
4. **The credential never passes through this repository or this chat.** The account
   holder generates it (Google Account → Security → 2-Step Verification → App passwords →
   "START-SYS"); the CTO places it in the Vercel Production scope and Bitwarden. Runbook 03
   row 11 owns rotation.

## Consequences

- **~500 recipients per day** from a consumer account (Google's published limit is
  approximate). A 600-member blast spans two days or needs Workspace. The send loop
  treats Gmail's 4xx deferrals as `throttled` and backs off rather than burning the queue.
- **No bounce webhooks.** Per-recipient status is `sent` / `failed` at the SMTP handshake;
  bounces arrive as mail in the START inbox. PRD item 25's "bounced" state is not
  populated by this transport. Reading the inbox for bounces is a later feature, if ever.
- **Spam risk.** Bulk, similar mail from a `gmail.com` address is exactly what filters
  look for. Plain-text alternatives are always sent, subjects vary with merge fields, and
  the composer is expected to keep the HTML simple.
- **A new dependency**, `nodemailer` (exact 9.1.1, plus `@types/nodemailer`). Justified by
  the above: hand-rolling SMTP over TLS would be a worse security decision than adding
  the library the whole Node ecosystem uses for it.
- **Launch position unchanged.** Resend plus an org domain remains the target
  (`ARCHITECTURE.md` §1, §4.2 deliverability). When OQ-10 is resolved: add
  `lib/mail/resend-transport.ts`, set `MAIL_TRANSPORT=resend`, retire the App Password.
  Nothing in the campaign code changes.
