# 2026-09-06 — Backup Tier 1 does not exist yet, and must be Pro before real data

**Status:** Open — hard launch blocker
**Severity:** High (Backup & Recovery NFR and Availability NFR both fail on this gap)
**Owner:** Project heads (budget decision) → `tech_admin` (provisioning)
**Raised by:** BUILD_PLAN S7-T15

---

## The honest position

**No hosted Supabase project for START-SYS exists yet.** This build has run against a
local `supabase start` Docker instance and, where noted, a scratch/preview project.
There is nothing today to be on the Free tier *or* the Pro tier — the question this
file answers is what plan the project must be on **the moment** a real, hosted
production project is created, before any real applicant or member data reaches it.

## Why Free is not an option at launch

ARCHITECTURE.md §1 and §7 already state the reasoning; this file exists so the
decision is recorded as a gap with an owner, not buried in a table only engineers
read.

1. **Supabase Free has no automated backups at all.** Tier 1 of the two-tier backup
   design (ARCHITECTURE.md §11) — Supabase's own daily automated backup — **requires
   the Pro plan**. On Free, Tier 1 simply does not exist.
2. **Supabase Free auto-pauses after 7 days of inactivity.** This system is
   genuinely idle for months between application periods (PRD §3, application
   windows open only during specific periods). A project that silently pauses itself
   is an Availability NFR failure that nobody would notice until the next
   application window opens and the portal does not respond.
3. **Nightly Tier 2 becomes the *only* tier on Free.** The off-provider `age`-encrypted
   dump to Backblaze B2 (`.github/workflows/scheduled.yml`, job `backup`) is designed
   to be the **second** independent tier, precisely so one provider's failure does
   not take down the only backup. On Free, it becomes the **only** backup — and its
   own secrets (`B2_KEY_ID`, `B2_APPLICATION_KEY`, `B2_BUCKET`, `B2_S3_ENDPOINT`,
   `SUPABASE_DB_URL`) are **also unprovisioned as of this writing** (no GitHub
   repository secrets have been set — the backup job's own preflight check fails
   loud and names exactly this).

## Current state, stated plainly

| Tier | Status |
|---|---|
| Tier 1 — Supabase automated daily backup (Pro only) | **Not available** — no hosted project exists; would not exist even if one did, because a plan decision has not been made |
| Tier 2 — nightly `age`-encrypted dump to Backblaze B2 | **Configured in code, not provisioned.** `.github/workflows/scheduled.yml`'s `backup` job exists, is written to fail loudly (not skip) when its secrets are absent, and — as of this writing — **its secrets are absent**, so every scheduled run to date has failed its preflight check and posted (or would post, if `DISCORD_WEBHOOK_URL` were also set) a failure notification. |

**Net position: zero backup tiers currently produce a usable, tested backup.** This is
not a hidden risk — it is the exact failure mode the job's own preflight check is
designed to surface loudly rather than mask, and this file is that surfacing.

## What "hard launch blocker" means here

This is not "nice to have before scaling up." It is: **do not point this system at a
real hosted Supabase project holding real applicant or member PII until:**

1. The project heads decide on and fund the Supabase **Pro** plan (~$25/mo baseline,
   ARCHITECTURE.md §10) — resolving `PRD.md` OQ-9 (who holds the budget).
2. The hosted Pro project is created under an **org-owned** identity (ARCHITECTURE.md
   §10, `docs/issues/2026-09-06-launch-debt.md`).
3. The five backup-job secrets (`SUPABASE_DB_URL`, `B2_KEY_ID`, `B2_APPLICATION_KEY`,
   `B2_BUCKET`, `B2_S3_ENDPOINT`) are provisioned as GitHub repository secrets per
   `docs/runbooks/03-CREDENTIAL_ROTATION.md` row 2 and row 6.
4. The `age` keypair is generated by the CTO and the public half committed to
   `keys/backup.age.pub`, replacing the placeholder the backup job's preflight check
   currently refuses to run against.
5. **The `backup` job has been manually dispatched at least once and completed
   green**, and **the restore drill in `docs/runbooks/02-RESTORE_FROM_BACKUP.md` has
   been performed at least once against a real object it produced** — an untested
   backup does not count (US-J4).

Until all five are true, this issue stays open and the system should be treated as
having **no working backup of any kind**, regardless of what the code in the repo is
capable of.

## Closing this issue

Do not delete this file when resolved — edit it to record: the date Pro was
purchased, the date the five secrets were provisioned, and a link to the first
successful `backup` job run and the first Drill record row in
`docs/runbooks/02-RESTORE_FROM_BACKUP.md`. A launch blocker closed without evidence is
indistinguishable from one nobody checked.
