# Runbook 02 — Restore From Backup

**Owner:** `tech_admin` (the CTO).
**Script:** `scripts/restore-drill.sh`
**Serves:** PRD v1.0 item 17, US-J4, US-K1; ARCHITECTURE.md §8, §11.

> **US-J4 does not say "backups are configured".** It says: *"A restore has actually been
> performed and recorded, not merely configured. An untested backup does not count."*
> The Drill record at the bottom of this file is the evidence. An unrecorded drill is
> indistinguishable from one that never happened.

---

## When to run this

- **Quarterly, whether or not anything is wrong.** An untested backup is not a backup.
  The drill is also the single highest-value hour of schema education in the whole
  handover — the incoming CTO learns the shape of the database by restoring it.
- **On real data loss, corruption, or a suspected attack** (PRD Backup & Recovery NFR).
  If you are here for that reason, read *"If it fails"* first and page the CTO.

## What backups exist

| Tier | What | Retention | Where |
|---|---|---|---|
| 1 | Supabase's own automated daily backup | 7 days | Supabase dashboard — **Pro plan only** |
| 2 | Nightly `pg_dump` → `age` → Backblaze B2 | 30 dailies + 12 monthlies | B2 bucket, `daily/` and `monthly/` |

**Check which tiers you actually have before you rely on both.** If the project is still
on the Supabase Free plan, Tier 1 does not exist — Free has no automated backups and
auto-pauses after 7 days idle — and Tier 2 is the only backup in the system. See
`docs/issues/2026-09-06-supabase-free-tier-backup-gap.md`; upgrading to Pro is a hard
launch blocker before real member data is collected.

Tier 2 is off-provider on purpose. Not the org's Google Drive, not Supabase: one lost
Google account at handover must not take both the proof-of-enrollment documents and the
backups (ARCHITECTURE.md §1).

---

## Preconditions

1. **`docker`, `age` and `psql` on your machine.** `supabase` on `PATH` is optional and
   unlocks the bonus pgTAP re-run — do install it; it is the strongest assertion in the
   drill.
2. **The private age key.** The repo commits only the public half
   (`keys/backup.age.pub`), which can encrypt and nothing else. The private half is held
   offline by the CTO and escrowed with the faculty adviser
   (`03-CREDENTIAL_ROTATION.md`). **Keep it outside the working tree**; nothing in this
   repository should ever be able to read it.
3. **B2 read access** — `B2_KEY_ID` / `B2_APPLICATION_KEY` / `B2_BUCKET` /
   `B2_S3_ENDPOINT` from Bitwarden. Not Vercel variables and not application config: the
   app never writes a backup, so it never holds the key that could delete one.
4. **About two hours, uninterrupted.** Most of it is waiting.
5. **A laptop you are willing to have PII on for an hour.** The decrypted dump is every
   scholar's birthdate, address, contact number and school ID number. The script keeps it
   in a `0700` temp directory and removes it on every exit path including Ctrl-C — but
   run this on an encrypted disk, and not on a shared machine.

## Steps

### 1. Confirm the recipient key is real (once, at setup)

```bash
grep -c REPLACE_ME_WITH_THE_REAL_PUBLIC_KEY keys/backup.age.pub   # must print 0
```

If it prints `1`, **no usable backup exists yet** and the nightly job has been failing
loudly for exactly this reason. Fix it before anything else:

```bash
age-keygen -o backup.age.key          # do NOT run this inside the repository
# Copy ONLY the "# public key: age1..." line into keys/backup.age.pub, commit it,
# then move backup.age.key to offline storage and escrow a copy with the adviser.
```

The keypair is generated by the CTO rather than by CI on purpose: the security property
is *custody* of the private half, and a key CI generated was, however briefly, somewhere
other than the CTO's hands.

### 2. List what is available and pick an object

```bash
export AWS_ACCESS_KEY_ID="$B2_KEY_ID"
export AWS_SECRET_ACCESS_KEY="$B2_APPLICATION_KEY"
export AWS_DEFAULT_REGION=us-east-005

aws --endpoint-url "$B2_S3_ENDPOINT" s3 ls "s3://${B2_BUCKET}/daily/"
aws --endpoint-url "$B2_S3_ENDPOINT" s3 ls "s3://${B2_BUCKET}/monthly/"
```

For a **quarterly drill**, take the most recent daily — the drill is about whether last
night's backup works, not whether an old one does.
For a **real restore**, take the newest object from *before* the damage.

### 3. Download it

```bash
mkdir -p backup
aws --endpoint-url "$B2_S3_ENDPOINT" s3 cp \
  "s3://${B2_BUCKET}/daily/startsys-YYYY-MM-DD.sql.age" backup/
```

A file of a few hundred kilobytes or more is expected. **A suspiciously small file is a
finding, not a convenience** — see *"If it fails"*.

### 4. Run the drill

```bash
scripts/restore-drill.sh backup/startsys-YYYY-MM-DD.sql.age /path/to/backup.age.key
```

It decrypts into a private temp directory, starts a throwaway `postgres:17` container
(matching production — restoring into another major version would prove something about
a database we do not run), creates the Supabase roles a stock Postgres lacks, loads the
dump, prints the five assertions, and destroys the container and the plaintext on exit.

### 5. Read the five assertions

| # | Assertion | What a failure means |
|---|---|---|
| 1 | `regions = 18` | Reference data did not survive. 18, not 17 — RA 12000 created the Negros Island Region (DATA_MODEL.md §6/0016). |
| 2 | 4 administrators, exactly CEO/COO/CTO/CCDO | The constitutional invariant did not survive (CBL Art. III §2). |
| 3 | `people > 0` | **A dump taken by a role subject to FORCE ROW LEVEL SECURITY restores an empty database that looks structurally perfect.** Check the role in `SUPABASE_DB_URL`. |
| 4 | `pg_policies > 0` | **The one nobody thinks to check.** Data restored, policies did not: every scholar's PII present with no RLS in front of it. It passes assertions 1–3. |
| 5 | RLS enabled **and** forced on every public table | ENABLE alone is not enough — a table owner bypasses non-forced RLS, and the migration role *is* the owner. |
| 6 | *(bonus)* the pgTAP suite is green against the restored database | The rows came back but the authorization model did not. |

The script exits `0` only when every assertion passed.

### 6. Record it below — this step is the requirement

Fill in a Drill record row: date, **your** name, the object, elapsed time, and paste the
PASS/FAIL block. For the quarterly drill this must be done **by someone who did not write
the script**, following only this page (US-K1, PRD Success Metric 7). If you had to ask
the outgoing officer a question, the runbook has a gap — fix the runbook in the same
sitting, while you still remember what was missing.

## How to verify it worked

- Five `PASS` lines and `RESULT: 5 passed, 0 failed` (six with the pgTAP bonus).
- The container is gone: `docker ps -a | grep startsys-restore-drill` prints nothing.
- The decrypted `.sql` no longer exists anywhere on disk.

For a **real restore into production**, the drill is only step one. Restoring into the
live project is a separate, deliberate act — take a fresh dump of the damaged database
first (you cannot get it back afterwards), and follow `05-INCIDENT_RESPONSE.md`. Never
restore over production on the strength of a drill alone.

## If it fails

| Symptom | Likely cause | Action |
|---|---|---|
| `age: no identity matched any of the recipients` | Wrong private key, or the public half was rotated without re-encrypting | Try the escrowed copy. **The archive is unreadable without the matching key — there is no recovery path.** |
| Assertion 3 fails, `people = 0` | The dumping role is subject to FORCE RLS | Fix the role in `SUPABASE_DB_URL` (`BYPASSRLS` / ownership) and re-run the backup job by hand. **Every prior nightly is equally empty.** Treat as an incident. |
| Assertion 4 fails, `pg_policies = 0` | Only the data half was dumped | The backup job dumps schema **then** data and concatenates. Confirm both `supabase db dump` invocations are present. **Same blast radius: every prior nightly is affected.** |
| Many `ERROR:` lines in the load log | Managed Supabase objects a stock container cannot replay | Expected and not fatal; the verdict is the five assertions, not `psql`'s exit code. A sudden *jump* in the count is still worth reading. |
| `docker: Cannot connect to the Docker daemon` | Docker not running | Start Docker Desktop. |
| No objects in `daily/` at all | The nightly job never ran, or has been failing | Check the `scheduled` workflow's run history. It fails loudly by design — if nobody saw it, `DISCORD_WEBHOOK_URL` is unset. **Treat as an incident: the org has had no Tier-2 backup for as long as that has been true.** |

Anything that turns out to be a real loss of data or a suspected compromise escalates to
[`05-INCIDENT_RESPONSE.md`](05-INCIDENT_RESPONSE.md), which carries the pre-drafted
72-hour NPC breach notification.
